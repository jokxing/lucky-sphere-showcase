# 精简技术导览

[返回案例首页](../README.md)

本项目围绕“活动准备 → 主持人开奖 → 结果查询”组织功能。这里说明设计和取舍，不依赖私有源码链接或本地服务。

## 技术组成

| 层次 | 技术 | 职责 |
| --- | --- | --- |
| 页面与交互 | Vue 3、TypeScript、Vue Router | 管理表单、舞台状态、结果展示 |
| 视觉场景 | Three.js / WebGL | 卡片球、中奖高亮、开奖动效 |
| 业务接口 | Fastify、TypeScript | 活动、名单、奖项与开奖请求处理 |
| 数据持久化 | Prisma、SQLite | 关系数据、事务与唯一约束 |
| 工程组织 | pnpm workspace | 前后端统一管理 |

业务数据与渲染职责分开：页面协调请求、进度和结果；3D 场景根据输入状态展示卡片与动效；最终中奖结果以服务端持久化记录为准。

## 四个关键设计

### 1. 总名额与每轮人数分开

累计总名额约束一个奖项最终能抽多少人，每轮默认人数只决定一次操作的期望人数。

例如总名额 5、每轮 2，实际依次抽取 2、2、1。实际人数同时受到候选人数和剩余奖项名额限制。全部奖项抽满后即可结束，不要求每位参与者都中奖。

### 2. 主持人确认切换

奖项抽满后保留末轮结果，推荐下一个有剩余名额的奖项，由主持人确认切换。确认动作只改变当前选择，下一轮仍需单独点击开始。

这样把“展示结果”“切换奖项”“发起开奖”三个动作分开，让现场主持节奏可控。结果已确认但数据尚未同步时，界面计入已知中奖者并限制继续抽取。

### 3. 幂等请求与事务约束

前端禁用按钮只能减少当前页面的重复点击，不能覆盖网络超时、重试或多个客户端操作。

服务端持久化开奖请求编号及原始人数：相同请求返回原结果，参数不一致时拒绝；末轮即使缩量，也保留原始请求参数用于后续核对。名额和候选人在 SQLite 写事务内重新检查，数据库唯一约束防止同一活动重复中奖。

已通过独立进程争抢名额的回归测试。该设计针对当前 SQLite 路径，迁移数据库或部署多实例仍需重新验证事务与冲突处理，不据此承诺高并发容量。

### 4. 视觉效果与可维护性

- 卡片展示顺序与业务开奖顺序分离，避免按名单编号展示时亮色过度集中；展示排序不改变中奖结果。
- 历史中奖高亮、单人及多人结果、彩纸效果分层处理，保留操作区的可用空间。
- 奖项进度复用同一份计算，桌面列表与窄屏选择保持一致；展示组件与页面业务协调分开。
- 限制渲染像素比；退出场景时取消动画、断开尺寸观察器并释放几何体、材质和纹理资源。
- 后台采用搜索、筛选与分页，导入前检查姓名列；异步刷新保留未保存草稿，危险操作提示影响范围。

## 如何看待验证结果

| 范围 | 已有验证 | 结论边界 |
| --- | --- | --- |
| 核心流程 | 本地真实 100 / 300 人导入、开奖、结果查询及重启核对 | 不代表生产并发能力 |
| 业务约束 | 末轮缩量、名额已满、请求重放、独立进程争抢、删除与重置 | 针对当前实现及 SQLite 路径 |
| 界面适配 | 桌面、125% 缩放和窄屏场景检查 | 目标设备连续动画仍以人工观察为准 |
| 大名单管理 | 此前 500 条模拟名单界面检查 | 不等同于 500 人真实全链路验收 |

源码项目已有 18 项 API 自动回归。案例材料以既有验收为依据；另为演示视频执行独立虚构活动的操作检查，没有重跑完整 API 回归或进行性能测量。

## 面向不同交流对象

**面试交流**：可重点展开组件职责、异步状态与草稿保护、3D 资源清理，以及重复请求为什么需要服务端幂等和数据库约束。实现包含 AI 辅助开发，按实际承担的需求、审查、理解与验收说明贡献。

**需求交流**：可围绕名单来源、奖项分轮规则、主持流程、结果公开范围和展示设备确认适配需求。账号权限、审计、备份、线上部署及长期运营需要另行评估；当前不包含真实支付业务。

本案例不提供私有源码入口、访问口令、数据库结构文件或部署配置。技术说明用于理解设计，不构成完整账号安全或抽奖公平性审计报告。
